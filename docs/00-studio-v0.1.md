## 0. 本轮范围声明

本方案 **只设计 Studio**。下列系统在后置轮次独立设计，本轮不展开：

- 赛题与盲测评测（独立评测系统）
- 用户榜与 Agent 榜（从评测派生）
- 论坛/社区/私信（独立社区系统）
- 帖子 AI 审核（先挂"会审"标牌，实现后置）

Studio 要回答的核心问题只有一个：

> **一个 11–16 岁的少年，如何在一个不写代码的界面里，定义、维护并迭代一支属于自己的 AI 队伍？**

评测、排名、社区都围绕"这支队伍"展开，但 Studio 本身必须先独立成立——**就算没有赛题和排行榜，孩子也应该愿意每天打开 Studio 调自己的队伍**。这是本轮的北极星。

## 1. 产品定位

### 1.1 一句话

ADVX Studio 是面向 11–16 岁少年的 **AI 队伍养成平台**：少年不写代码，在一个可视化的"组队室"里定义自己的 AI 队伍——有哪些角色、每个角色叫什么名字、能用什么工具、怎么协作——然后维护它、迭代它、让它越来越强、越来越像自己。

### 1.2 与"AI 工具"的本质区别

| 市面现状 | ADVX Studio |
|---|---|
| 孩子拿到一个 AI 工具，当使用者 | 孩子拥有一支 AI 队伍，当队长 |
| 一个万能助手，用完即弃 | 一支可演化、可版本化、有名字有性格的队伍 |
| 孩子和 AI 单线聊天 | 孩子指挥多个角色协作完成任务 |
| 没有积累、无法证明 | 队伍是长期资产，版本可追溯 |
| 孩子不懂发生了什么 | 孩子是决策者，每次修改都有后果 |

### 1.3 slogan 落地

> 别人给孩子一个 AI 工具，我们给孩子一支 AI 队伍，以及成为队长的责任。

"队长的责任"在 Studio 里具体表现为：

- 给每个角色起名字、定义职责——**对队伍有所有权**
- 选择角色能用什么工具——**对能力边界有控制权**
- 决定队伍里加几个角色、删哪个——**对组织结构有决策权**
- 看到队伍在任务里的表现后迭代——**对成长有责任感**

"责任"不是负担，是让孩子从"用 AI"变成"经营 AI"的认知跃迁。

## 2. 核心概念

### 2.1 术语表

| 术语 | 含义 | 对应 Paperclip 底座 |
|---|---|---|
| **队队伍（Team）** | 一个少年拥有的整套 AI 队伍，长期演化 | `Company` |
| **队员（Agent）** | 队伍里的一个角色实例，有名字、职责、工具 | `Agent` |
| **角色模板（Role Template）** | 预制角色定义，如"侦察员/点子员/搭建员/挑刺员"，用户可基于模板创建队员 | Paperclip `built-ins/agents` + `teams-catalog` |
| **工具（Tool）** | 队员可调用的能力，如"搜索/写代码/画图/读文件" | Paperclip `MCP Server` + `Plugins` |
| **Skill** | 队员可挂载的技能模块，描述"怎么干活" | Paperclip `skills-catalog` |
| **任务（Task）** | 一次让队伍干活的事件——可以是生活任务、练习、赛题、发帖 | Paperclip `Issue` |
| **Run** | 一次任务的实际执行，产生事件、产物、日志 | Paperclip `Heartbeat Run` |
| **产物（Work Product）** | Run 产出的东西——微工具、帖子、报告、图片 | Paperclip `Work Product / Artifact` |
| **活动记录（Activity）** | 所有操作的不可变审计日志 | Paperclip `Activity & Events` |
| **队长（Captain）** | 少年用户本人，队队伍的所有者与决策者 | Paperclip `Board User` |

### 2.2 关键关系

```
队长（少年）
 └─ 拥有 → 1 支 队伍（Team）
            ├─ 包含 → N 个 队员（Agent）
            │         ├─ 角色（来自模板 or 自定义）
            │         ├─ 名字（用户起）
            │         ├─ 工具清单（用户选）
            │         ├─ Skill 清单（用户挂）
            │         └─ 协作关系（向谁汇报/委托给谁）
            └─ 版本演化 → 多个版本快照
                          └─ 每次修改都可封存、可回溯

任务（Task）→ 绑定队伍当前版本 → 产生 Run → 产生产物 + 活动记录
```

### 2.3 与旧方案术语对照

旧方案用 "Harness Family / Harness Version / Harness Studio"，新方案统一改用更儿童友好的"队伍/队员/组队室"：

| 旧方案 | 新方案 |
|---|---|
| Harness Family | 队伍（Team）|
| Harness Version | 队伍版本快照 |
| Harness Studio | 组队室（Studio）|
| Agent（单角色实例）| 队员 |
| 固定四角色 | 四角色模板（起步，可加/删）|
| Credits/预算 | **砍除** |
| Life Mission | 生活任务（后置轮设计）|
| Challenge | 赛题（后置轮设计）|

## 3. 核心循环

Studio 本身的循环，不含评测和社区：

```
进入组队室
 → 看到自己的队队伍（首次为空，引导从模板起步）
 → 加/删/改名/配工具（编辑队伍）
 → 试跑一次（让队伍跑个小任务看表现）
 → 看活动记录与产物（队伍干了什么、干得怎样）
 → 迭代（改队员/换工具/调协作）
 → 封存版本（可回溯的快照）
 → 回到编辑
```

**关键设计意图**：

- **试跑**是 Studio 的灵魂：改完队伍立刻能跑一次看效果，让孩子形成"改 → 试 → 看 → 再改"的迭代肌肉。试跑任务可以由平台预置（"跑个 hello world"级别的），也可以后置轮接生活任务/赛题。
- **封存版本**是长期资产的锚点：孩子知道"这个版本是我上次调好的"，下次可以基于它继续改。版本不进排行榜（排行榜后置），但版本让"我的队伍在变强"这件事可感知。
- **活动记录与产物**是"队长责任"的载体：孩子看到的不是模糊的"AI 帮你做了"，而是"侦察员查了什么、点子员提了什么、搭建员做了什么"——每个角色都可追溯。

## 4. 组队室（Studio）配置模型

这是本轮的核心交付。Studio 暴露给孩子配置的**全部字段**如下，分四组：

### 4.1 队伍层（Team-level）

| 配置项 | 说明 | 默认 | 是否可改 |
|---|---|---|---|
| 队伍名 | 用户给整支队伍起的名字 | "我的 AI 队伍" | ✓ |
| 队伍简介 | 一句话描述这支队伍要干什么 | 空 | ✓ |
| 底层模型 | 队伍所有队员共享的底层模型 | 平台内置（如 DeepSeek） | ✓（仅平台内置清单内选）|

> **模型策略说明**：所有用户共享同一平台内置模型清单（如只有一个 DeepSeek 选项），用户选择不改公平性（大家都能选一样的），但给孩子"我的队伍用哪个模型"的决策感。预算/Credits 机制**完全砍除**。

### 4.2 队员层（Agent-level）

每个队员是一个角色实例，可从模板创建或从零自建：

| 配置项 | 说明 | 是否必填 |
|---|---|---|
| 队员名 | 用户给这个角色起的名字（如"小雷达""主意王"）| 必填 |
| 角色模板 | 创建时选的模板（侦察员/点子员/搭建员/挑刺员/自定义）| 创建时必选，之后可改 |
| 职责描述 | 一段话描述这个队员干什么 | 必填（模板有默认值，可改）|
| 工具清单 | 这个队员能调用的工具（从平台工具库选）| 必填（模板有默认值，可改）|
| Skill 清单 | 这个队员挂载的技能模块 | 选填 |
| 协作关系 | 向谁汇报、能委托给谁 | 选填（模板有默认值）|

**角色模板**（起步四角色，用户可基于模板创建或自建新角色）：

| 模板 | 职责默认 | 默认工具 | 默认协作 |
|---|---|---|---|
| 侦察员（Scout）| 查清事实、找约束 | 搜索、读文件 | 向点子员汇报 |
| 点子员（Inventor）| 出主意、想方案 | 搜索、画图 | 接收侦察员、委托搭建员 |
| 搭建员（Builder）| 把方案做出来 | 写代码、画图、写文档 | 接收点子员委托 |
| 挑刺员（Critic）| 挑毛病、质检，不能自己改产物 | 读文件、跑测试 | 向队长汇报问题 |
| 自定义 | 用户写 | 用户选 | 用户配 |

**加/删规则**：
- 用户可随时加新队员（从模板或从零）
- 用户可随时删队员
- 一支队伍最少 1 个队员，最多暂定 8 个（防止认知过载）
- 删除队员不影响历史版本快照（快照是只读的）

### 4.3 协作层（Collaboration）

旧方案叫 Captain Playbook。简化版：

| 配置项 | 说明 |
|---|---|
| 汇报线 | 队员之间的汇报关系（A 向 B 汇报）|
| 委托权限 | 哪些队员可以把任务委托给谁 |
| 决策位 | **后置**：当前不暴露"关键岔路口"概念，默认队员遇到不确定就停下发起"问队长"——这条 P0 可不暴露给孩子，只实现"队员卡住时暂停并通知队长" |

> 当前 Studio **不暴露"审批门/Gate"给孩子**。底层 Paperclip 的 Governance & Approvals 原样保留，但默认配置为"队员遇不确定自动暂停"，不让孩子配策略。这保护儿童可控性，等评测轮再开。

### 4.4 试跑层（Test Run）

| 配置项 | 说明 |
|---|---|
| 试跑任务 | 平台预置的几个小任务（"做个待办清单""画张图"级别），让用户改完队伍立刻能试 |
| 试跑结果 | 展示每个队员干了什么（活动记录）+ 最终产物 |
| 版本封存 | 试跑满意后可"封存当前队伍"为一个版本快照 |

> 试跑不评分、不进榜、不公开，纯粹是给孩子"改 → 试 → 看"的反馈循环。

## 5. 工程架构

### 5.1 复用判定三层

| 层 | Paperclip 给的 | 你的处理 |
|---|---|---|
| **L1 底层调度** | Heartbeat 执行队列、原子 checkout、workspace 隔离、secret 注入、cost tracking、audit trail、orphan 恢复 | **原样用**。但 cost tracking 模块关停显示（预算砍了，底层 trace 仍保留用于未来诊断，不给孩子看）|
| **L2 中层语义** | Company/Agent/Issue/Work Product/Activity/Governance/Skill/Org Chart | **术语映射**：Company→Team、Agent→队员、Board User→队长。数据模型不动，只改 API/UI 文案和字段命名 |
| **L3 顶层 UX** | React 企业仪表盘 | **完全弃用**，自写面向儿童的组队室前端 |

### 5.2 仓库结构（建议）

```
advx26/                          # 你的产品仓库（Fork Paperclip 起步）
├── server/                      # Paperclip server，原样保留 + 魔改
│   └── src/
│       ├── routes/              # 加 /studio/* 路由（队队伍 CRUD）
│       ├── services/            # 加 team-service / agent-service 等
│       └── built-ins/agents/    # 加四角色模板定义
├── ui/                          # Paperclip 原 UI，弃用，仅留构建链兼容
├── ui-advx/                     # 自写儿童化前端（React + Vite）
│   └── src/
│       ├── pages/               # 组队室/试跑/活动记录/版本
│       ├── components/          # 队员卡片/工具选择器/角色模板库
│       └── ...
├── packages/                    # Paperclip workspace packages，原样用
│   ├── adapters/                # agent adapter，原样用
│   ├── mcp-server/              # MCP 工具网关，原样用
│   ├── skills-catalog/          # 内置 skills，原样用 + 加自有 skills
│   └── teams-catalog/           # 加四角色 team 模板
└── docs/                        # 本方案文档
```

### 5.3 数据模型（基于 Paperclip，不改 schema，只改语义）

| Paperclip 表 | ADVX 语义 | 备注 |
|---|---|---|
| `companies` | 队伍 | 每个少年 1 支队伍（一对一映射）|
| `agents` | 队员 | 字段含 `name`（用户起）、`role`（模板）、`adapterType` |
| `issues` | 任务 | `team_id`/`agent_id` 链不动 |
| `work_products` | 产物 | 不动 |
| `activity_log` | 活动记录 | 不动 |
| `agents` 的 `config` JSON | 队员配置（工具清单、Skill、协作）| 加自定义字段，但不破坏 Paperclip schema |

> **关键原则**：不删 Paperclip 表、不破坏 Paperclip schema 约束，只在 JSON config 字段里加 ADVX 自有字段。这样万一未来要吃上游某 bugfix 也不至于完全断（虽然你已说不跟上游）。

### 5.4 前端栈选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 框架 | React + Vite | 与 Paperclip UI 同栈，方便复用其部分组件逻辑 |
| UI 库 | 自写组件 + Tailwind v4 token 体系 | 遵循 Paperclip DESIGN.md 的 token-only 原则 |
| 状态 | 轻量自管（Zustand 或 React Context）| Studio 状态不复杂，不引入重框架 |
| 路由 | React Router | 标准选型 |
| 设计语言 | 见 `docs/03-design-language.md`（后置）| 本轮先不定视觉，只定信息架构 |

## 7. 角色自定义深度（推翻旧方案 P08/P09）

旧方案 P08（Contract+Policy 不暴露 Prompt/模型参数）和 P09（固定四角色）**正式推翻**。新规则：

| 旧方案 | 新方案 |
|---|---|
| 固定四角色，用户不管理实例数 | 四角色模板起步，用户可加/删角色 |
| 不暴露 Prompt/模型参数 | 仍不暴露 Prompt 和模型参数，但暴露"工具清单"和"Skill 挂载"|
| 预算系统 | **完全砍除** |
| 底层模型不可选 | 平台内置模型清单内可选 |
| Gate/审批门用户配置 | **暂不暴露给孩子**，底层保留，默认"卡住就暂停问队长" |

**孩子能配的 vs 不能配的**：

| 孩子能配 | 孩子不能配 |
|---|---|
| 加/删队员 | 系统 Prompt |
| 给队员起名 | 模型参数（temperature 等）|
| 选角色模板 | 预算（砍了）|
| 选工具清单 | 审批门策略（暂不暴露）|
| 挂 Skill | 底层模型（仅平台清单内选）|
| 配协作关系 | 直接写代码/节点画布 |

> 边界哲学：孩子配"谁、有什么工具、怎么协作"——**组织决策**；不配"模型怎么想、参数怎么调、预算怎么花"——**技术决策**。这样既给所有权，又不让认知负担压垮 11 岁。

## 8. 开放问题（本轮留待回答）

以下问题不阻塞 Studio v0.1 骨架落地，但会在下一轮细化时影响细节，列在这里待答：

### Q-01｜四角色模板之外，第一批要预置多少角色模板？
四角色模板能覆盖"做微工具"场景，但"写论坛帖""做研究分析"等场景需要什么新模板？要不要在 Studio 轮就预置，还是等社区/评测轮再加？

### Q-02｜队员上限 8 个是否合适？
8 是防认知过载的拍脑袋值。11 岁和 16 岁是否应该有不同上限？还是统一一个值？

### Q-03｜试跑任务预置几个？什么级别？
"做个待办清单""画张图"是否太轻？要不要至少有一个"让队伍协作完成一个小微工具"的试跑，才能真验证队伍配置差异？

### Q-04｜版本快照的封存频率与存储成本？
孩子可能频繁改队伍，每次试跑满意都封存一个版本，存储和版本管理是否需要限制（如最多保留 20 个版本）？

### Q-05｜协作关系 UI 如何面向 11 岁可视化？
"汇报线/委托权限"在企业产品里是组织架构图，给孩子要不要做成更游戏化的"队员关系图"？是否需要拖拽连线？

### Q-06｜队员卡住"问队长"的交互形态？
底层是 Paperclip Governance 的 approval gate，但孩子看到的应该是什么？弹窗？任务卡？通知？这条影响 Studio 的通知系统设计。

### Q-07｜论坛写帖 Agent 在 Studio 里的位置？
你说论坛写帖 Agent 也是用户自定义、有模板。它是：
- (a) Studio 主队伍里的一个角色（用户把"写帖员"加进主队伍）
- (b) Studio 里单独挂的一个固定功能 Agent（不参与主队伍版本演化）
- (c) Studio 里有第二个 tab"我的写帖 Agent"，独立配置

这条决定 Studio 的信息架构要不要分主次。
